# Passkeys and saved passwords

**Goal:** websites in Sela can sign you in and sign you up with passkeys from the Passwords app, iCloud Keychain or another password manager, the way they do in Safari, Chrome and Arc.

**Where it stands:** everything is built and sits behind one switch, the entitlement `com.apple.developer.web-browser.public-key-credential`. Apple grants it per team, and team KNU6L342KX doesn't have it yet. The build Sela ships today isn't signed with it, so it hides the new settings and behaves exactly as before. Turning it on is a signing change, described in "Switching it on" below. No code changes.

**Sources:** the macOS 27 SDK in Xcode 27 on this Mac, the AuthenticationServices and WebKit headers and Swift interfaces, the entitlements and provisioning profiles inside Chrome and Arc, and the strings in macOS's AuthenticationServicesCore and System Settings.

## What macOS needs from a browser

### Passkeys on websites

- WebKit implements `navigator.credentials.create()` and `navigator.credentials.get()` in every `WKWebView`. Sela doesn't write any of it. WebKit passes each request to macOS's AuthenticationServices agent, which shows the system sheet over the web view's window, lets the user pick the Passwords app, another credential provider, a security key or a phone, and returns the result to the page.
- For an app that isn't Safari, the agent serves a request for any website only when the app holds `com.apple.developer.web-browser.public-key-credential`. AuthenticationServicesCore checks for that entitlement by name. Without it, an app gets passkeys only for domains in its own `webcredentials:` associated domains, which can't cover the whole web.
- It's a managed, restricted entitlement. Apple has to approve it for the team, and macOS only honours it in an app that also embeds a provisioning profile allowing it. Chrome and Arc are both signed this way. Chrome's profile is a Developer ID profile, `ProvisionsAllDevices` true, so outside the App Store works.
- Restricted entitlements also need `com.apple.application-identifier` set to `TEAM.bundle-id` and `com.apple.developer.team-identifier` set to the team, matching the profile.
- Profiles in Sela share the passkeys. They live in the Passwords app or the provider, not in a `WKWebsiteDataStore`, so every profile sees the same ones.
- WebKit also handles conditional mediation, which is the passkey suggestions in a sign-in field, and the WebAuthn signal APIs such as `PublicKeyCredential.signalUnknownCredential`.

### Seeing which sites have passkeys

`ASAuthorizationWebBrowserPublicKeyCredentialManager`, macOS 13.3 or later, is the browser's own view of the passkeys the user saved:

- `requestAuthorizationForPublicKeyCredentials(_:)` asks the user once and calls back with an `AuthorizationState`, which is `.authorized`, `.denied` or `.notDetermined`.
- `authorizationStateForPlatformCredentials` reads the current state without asking.
- `platformCredentials(forRelyingParty:) async` lists the passkeys for one site as `ASAuthorizationWebBrowserPlatformPublicKeyCredential` values, each with `name`, `customTitle`, `relyingParty`, `credentialID`, `userHandle` and `providerName`. It returns nothing until the user allows access.
- `isDeviceConfiguredForPasskeys`, macOS 26.2 or later, says whether this Mac has anywhere to keep passkeys.
- The choice is a privacy permission, the TCC service `kTCCServiceWebBrowserPublicKeyCredential`. The user changes it in System Settings > Privacy & Security > Passkeys Access for Web Browsers, whose URL is `x-apple.systempreferences:com.apple.preference.security?Privacy_PasskeyAccess`. System Settings says a change applies once the browser quits.
- The manager needs the same entitlement. Signing in on a website doesn't need this permission. What it adds is the list, which a browser uses to show passkeys in its own interface, and which macOS may also use for the suggestions in sign-in fields. Check that once the entitlement is on.
- Browsers that implement WebAuthn themselves, like Chrome, build requests with `ASAuthorizationWebBrowserPlatformPublicKeyCredentialProvider` and `ASPublicKeyCredentialClientData`, which carries the page's origin. Sela doesn't need those, because WebKit makes the requests.

### Saved passwords

There is no way today for a browser other than Safari to fill in passwords from the Passwords app on any website. The SDK offers these, and none of them fits:

- `ASAuthorizationPasswordProvider` and `ASAuthorizationController` give an app the passwords for its own associated domains only.
- `SecRequestSharedWebCredential` is the same, and was removed from macOS in 11.
- `SecAddSharedWebCredential` and its replacement `ASCredentialDataManager.save(password:for:title:anchor:)` save a password for the app's associated domains. The replacement isn't available on macOS.
- `ASCredentialIdentityStore`, `ASCredentialProviderViewController` and `ASSettingsHelper` are for apps that *are* password managers, offering their passwords to Safari and other apps.
- `WKWebView` doesn't show AutoFill for passwords on macOS. AppKit's AutoFill in `NSTextField` with `contentType = .username` or `.password` works in native fields only, and still only for associated domains.
- macOS 27 adds `WKContentWorld.Configuration.autofillScriptingEnabled`, so scripts in an app's own content world can start AutoFill, and `webView(_:willSubmitForm:submissionHandler:)` with `WKFormInfo`, which shows a browser the fields a form submits. Neither reads the Passwords app. They're what a browser would need to build its own password manager, which is out of scope here. Both need macOS 27, while Sela supports macOS 15.

So the Passwords settings tab says plainly that Sela can't fill in saved passwords, and points to the Passwords app and to password managers' Web Extensions, which Sela can already run on macOS 15.4 or later. A manager that only ships a Safari App Extension, or needs native messaging with its app, may not work.

## What Sela does

- `Passkeys`, a new package module with no other dependencies:
  - `PasskeyEntitlement.isPresent` reads the entitlement from Sela's own signature with `SecTaskCreateFromSelf` and `SecTaskCopyValueForEntitlement`, once per launch. Only the Boolean true counts.
  - `PasskeyAccess` is the user's choice, and `SystemPasskeyAccess` gets it from `ASAuthorizationWebBrowserPublicKeyCredentialManager`, asks for it, and lists a site's passkeys for later use.
  - `PasskeyAccessModel` is the Settings row: the status, the button, and the line explaining what to do next. Swift Testing tests in `PasskeysTests` cover it with a stand-in source.
- `WebKitEngine.servesPasskeys` says whether pages get passkeys. WebKit needs no extra configuration. Every tab's `WKWebView` already passes requests on, and macOS shows its sheet over the tab's window.
- The app makes a `PasskeyAccessModel` only when `servesPasskeys` is true. Settings then shows a Passwords tab with a "Passkey access" row:
  - not asked yet, with an Allow Access button that shows macOS's prompt
  - allowed, with no button
  - not allowed, with an Open Privacy Settings button and the steps to change it
  - a warning when the Mac has nowhere to keep passkeys
  The row reads the state again whenever Sela comes to the front, since the user may have changed it in System Settings.
- Sela never asks for access by itself. The user asks from Settings.
- In a build without the entitlement there's no Passwords tab and nothing calls AuthenticationServices. Pages see WebKit's usual refusals, as they do today.

## Switching it on

1. **Ask Apple for the entitlement.** Apple grants managed entitlements on request, from the team's Account Holder. Look for the web browser public key credential capability under Capability Requests on the App ID's page in Certificates, Identifiers & Profiles. If it isn't offered there, ask through developer.apple.com/contact. Give the team ID KNU6L342KX and the bundle ID `app.brow.Brow`, and say that Sela is a web browser for macOS distributed with Developer ID, with links to the website and the source. Approval can take weeks. Once it's approved, the capability shows on the App ID's page.
2. **Turn it on for the App ID.** In Certificates, Identifiers & Profiles, open the identifier `app.brow.Brow` and tick the web browser public key credential capability. Make the App ID first if it doesn't exist, as an explicit App ID for macOS.
3. **Make a Developer ID provisioning profile.** Under Profiles, add a profile, choose Developer ID under Distribution, pick `app.brow.Brow` and the Developer ID Application certificate, and download it. Keep the file out of git. Check it with `security cms -D -i Sela.provisionprofile` and look for `com.apple.developer.web-browser.public-key-credential` under `Entitlements`. Whenever the certificate is renewed, make a new profile.
4. **Build a release with it on your Mac.** Run `SELA_PASSKEYS=1 SELA_PROFILE=~/path/to/Sela.provisionprofile scripts/release.sh KNU6L342KX`. With `SELA_PASSKEYS=1`, release.sh checks that the profile carries the entitlement, is for `KNU6L342KX.app.brow.Brow` and is a Developer ID profile, and stops if not. It fills the team and bundle ID into `app/Support/Sela-Passkeys.entitlements`, puts the profile in the app as `Contents/embedded.provisionprofile`, and signs with those entitlements instead of `Sela.entitlements`. Without the variable, release.sh does exactly what it did before.
5. **Check the build before publishing it.**
   - `codesign -d --entitlements - .build/release/Build/Products/Release/Sela.app` lists the entitlement.
   - Sela opens. If macOS refuses to open it, the profile and entitlements don't match.
   - Settings shows a Passwords tab, and Allow Access shows macOS's prompt.
   - On webauthn.io, registering and then signing in with a passkey works.
   - On a site with conditional mediation, like github.com's sign-in page, the username field offers your passkey. Note here whether that needs access to be allowed.
6. **Do the same in the Release workflow.** Add the profile as a repository secret `SELA_PROFILE_BASE64`, made with `base64 -i Sela.provisionprofile`. In `.github/workflows/release.yml`, decode it in the "Put the signing certificate and keys in place" step to `$RUNNER_TEMP/Sela.provisionprofile`, delete it in "Remove the keys", and add `SELA_PASSKEYS: "1"` and `SELA_PROFILE: ${{ runner.temp }}/Sela.provisionprofile` to the build step's `env`.
7. **Keep the two entitlements files in step.** Anything added to `Sela.entitlements` later goes in `Sela-Passkeys.entitlements` too, and the other way round. Once the switch has shipped and works, make `Sela-Passkeys.entitlements` the only file and drop `SELA_PASSKEYS`.

To try it in Debug before a release, sign with an Apple Development certificate and a macOS development profile for `app.brow.Brow` that includes the capability, and set `CODE_SIGN_ENTITLEMENTS = Support/Sela-Passkeys.entitlements` in `app/Support/Signing.local.xcconfig`. Xcode fills in the team and bundle ID itself.

## Limits

- Passkeys need macOS to have the entitlement on Sela's signature. A copy Sela built ad hoc on someone's own Mac won't get them.
- A copy signed with the entitlement but missing the profile won't open at all, which is why release.sh checks the profile first.
- Sela can list a site's passkeys once access is allowed, but doesn't show them anywhere yet. The command bar or the address bar could later.
- Saved passwords need either Apple to open Passwords app AutoFill to other browsers, or Sela to keep its own passwords with the macOS 27 form APIs. Neither is planned.
